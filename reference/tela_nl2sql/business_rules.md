## 2. Platform Core Safety & Execution Rules

### RULE-001: Pure-Read Single-Statement AST Validation
- **Domain Area:** SQL Safety & Query Validation
- **Statement:** Any SQL query generated by the AI or submitted for execution must parse as exactly one statement, and that statement must be an AST `Select` or CTE `With ... Select`. Any statement containing data manipulation, schema definition, session configuration, or multiple semicolons is strictly prohibited.
- **Source Location:** `backend/app/validator.py:48-124`, `PlanFiles/05 §2`
- **Status:** Implemented (Verified L5)
- **Inputs:** `sql` (string), `dialect` (string: postgres, mysql, clickhouse, duckdb)
- **Constraint / Logic:**
  ```text
  parsed_statements = sqlglot.parse(sql, read=dialect)
  if len(parsed_statements) != 1:
      REJECT("Multi-statement query detected")
  if not isinstance(parsed_statements[0], (exp.Select, exp.With)):
      REJECT("Statement is not a read-only SELECT")
  if any(node in FORBIDDEN_AST_NODES for node in parsed_statements[0].walk()):
      REJECT("Forbidden AST operation detected")
  ```
- **Forbidden AST Nodes:** `Insert`, `Update`, `Delete`, `Drop`, `Alter`, `Create`, `Truncate`, `Grant`, `Revoke`, `Merge`, `Command`, `Transaction`.
- **Worked Example:**
  - *Input SQL:* `SELECT COUNT(*) FROM users; DROP TABLE users;`
  - *Parser Evaluation:* Produces two root AST statements.
  - *Result:* Rejected at statement-count check (`len == 2`); `approved = False`, `is_security_event = True`.

### RULE-002: Semantic Layer Table & Column Allow-List Enforcement
- **Domain Area:** Schema Guardrails & Anti-Hallucination
- **Statement:** Every table and column identifier referenced anywhere in the executable SQL query must exist in the active connection's approved semantic layer subset.
- **Source Location:** `backend/app/validator.py:126-175`, `PlanFiles/05 §2.4`
- **Status:** Implemented (Verified L3)
- **Inputs:** `query_ast`, `allowed_tables` (Set[str]), `allowed_columns` (Dict[str, Set[str]])
- **Constraint / Logic:**
  ```text
  referenced_tables = extract_tables(query_ast)
  if not referenced_tables.issubset(allowed_tables):
      REJECT("Query references unapproved or non-existent tables: " + (referenced_tables - allowed_tables))
  ```
- **Worked Example:**
  - *Context:* Approved tables = `{"financial_transaction", "merchant"}`.
  - *Input SQL:* `SELECT ft.amount, s.name FROM financial_transaction ft JOIN stakeholder s ON ft.id = s.id`
  - *Result:* Table `stakeholder` is not in the allow-list. Query is rejected before execution (`rejection_stage = "allow_list"`).

### RULE-003: Deterministic Row Limit Injection
- **Domain Area:** Database Resource Protection
- **Statement:** If an approved query lacks a `LIMIT` clause, the validator must inject a dialect-specific limit clause capping maximum rows returned to 10,000.
- **Source Location:** `backend/app/validator.py:_inject_limit`, `PlanFiles/05 §2.6`
- **Status:** Implemented (Verified L3)
- **Inputs:** `query_ast`, `default_limit = 10000`
- **Constraint / Logic:**
  ```text
  if query_ast.args.get("limit") is None:
      query_ast.set("limit", exp.Limit(this=exp.Literal.number(default_limit)))
  ```
- **Worked Example:**
  - *Original Query:* `SELECT financial_txn_id, amount FROM financial_transaction`
  - *Modified Query:* `SELECT financial_txn_id, amount FROM financial_transaction LIMIT 10000`
  - *Execution Output:* If `row_count == 10000`, the execution engine marks `truncated = True`.

### RULE-004: Fail-Closed Row-Level Security via AST Subquery Substitution
- **Domain Area:** Data Security & Multi-Tenant Access Control
- **Statement:** For non-admin users with row-level restrictions on a table `t`, every reference to `t` in the query AST must be rewritten as a subquery `(SELECT * FROM t WHERE <predicates>) AS t`. If the query cannot be rewritten, contains CTEs that shadow table `t`, or references unresolvable dynamic user attributes, execution must fail closed.
- **Source Location:** `backend/app/access.py:apply_row_filters`, `backend/app/query_guard.py`
- **Status:** Implemented (Verified L3)
- **Inputs:** `query_ast`, `user_row_rules` (Dict[table, List[Condition]]), `user_attributes` (Dict[str, Any])
- **Predicate Resolution:**
  ```text
  Condition: {column: "outlet_id", op: "eq", value: {"attr": "assigned_outlet"}}
  Resolved Value: user_attributes.get("assigned_outlet")
  If resolved value is None or empty:
      Refuse Query (RowRuleError)
  ```
- **AST Transformation Formula:**
  ```text
  FROM financial_transaction ft
  ===>
  FROM (
      SELECT * FROM financial_transaction 
      WHERE outlet_id = 'OUT-992'
  ) AS ft
  ```
- **Worked Example:**
  - *User Attributes:* `assigned_outlet = 'OUT-992'`
  - *User Query:* `SELECT SUM(amount) FROM financial_transaction WHERE txn_date >= '2026-01-01'`
  - *Rewritten Query:*
    ```sql
    SELECT SUM(amount) 
    FROM (
        SELECT * FROM financial_transaction 
        WHERE outlet_id = 'OUT-992'
    ) AS financial_transaction 
    WHERE txn_date >= '2026-01-01'
    ```
  - *Fail-Closed Edge Case:* If user has no `assigned_outlet` attribute defined, `apply_row_filters` raises `RowRuleError("Could not apply your data rules to this query, so it was not run.")`.

## 3. Payments Domain Business Rules & Grain Specifications

### RULE-007: Golden Grain Rule G1 – Transaction Fact Table Counting
- **Domain Area:** Payments Core Domain
- **Statement:** `financial_transaction` is the aggregate root. `COUNT(*)` is valid if and only if `financial_transaction` is the sole table or joined strictly to 1:1 / N:1 dimension tables. When joined to 1:N child tables, counting must use `COUNT(DISTINCT ft.financial_txn_id)`.
- **Source Location:** `payments.txt §2`
- **Status:** Documented & Enforced (Verified L3)
- **Entity Multipliers:**
  - `financial_transaction` (ft): 1 (Grain Root)
  - `authorization_message` (a): 1:N
  - `clearing_message` (cm): 1:N
  - `transaction_fee` (tf): 1:N
  - `settlement_line` (sl): 1:N
- **Worked Example:**
  - *Incorrect Query:*
    ```sql
    SELECT COUNT(*) 
    FROM financial_transaction ft 
    JOIN transaction_fee tf ON ft.financial_txn_id = tf.financial_txn_id
    ```
    *Flaw:* If a transaction has 3 fee components (MDR, Scheme, Interchange), `COUNT(*)` returns 3 instead of 1.
  - *Correct Query:*
    ```sql
    SELECT COUNT(DISTINCT ft.financial_txn_id) 
    FROM financial_transaction ft 
    JOIN transaction_fee tf ON ft.financial_txn_id = tf.financial_txn_id
    ```

### RULE-008: Golden Grain Rule G2 – Fact Amount Summation Across 1:N Joins
- **Domain Area:** Payments Financial Calculations
- **Statement:** Never execute `SUM(ft.amount)` across 1:N child tables (`transaction_fee`, `settlement_line`, `authorization_message`). Child tables must be pre-aggregated in Common Table Expressions (CTEs) before joining to `financial_transaction`.
- **Source Location:** `payments.txt §2 (G2)`
- **Status:** Documented & Enforced (Verified L3)
- **Calculation Formula:**
  ```text
  Total Transaction Amount = SUM(ft.amount) from ft alone
  Total Fees = SUM(tf.fee_amount) from pre-aggregated CTE
  ```
- **Worked Numerical Example:**
  - Transaction #1: Amount = AED 1,000. Fees: Interchange = AED 15, Scheme = AED 2, MDR = AED 25 (3 rows).
  - *Incorrect Direct Join:* `SUM(ft.amount)` computes `AED 1,000 * 3 = AED 3,000` (Overstated by 200%).
  - *Correct CTE Approach:*
    ```sql
    WITH fee_summary AS (
        SELECT financial_txn_id, SUM(fee_amount) AS total_fee
        FROM transaction_fee
        GROUP BY financial_txn_id
    )
    SELECT 
        SUM(ft.amount) AS gross_volume,
        SUM(fs.total_fee) AS total_fees
    FROM financial_transaction ft
    LEFT JOIN fee_summary fs ON ft.financial_txn_id = fs.financial_txn_id;
    ```
  - *Output:* Gross Volume = AED 1,000, Total Fees = AED 42.

---

### RULE-009: Golden Grain Rule G3 – Multi-Domain Independence
- **Domain Area:** Payments Cross-Domain Aggregation
- **Statement:** Never join two independent 1:N child tables directly (e.g., `refund` and `dispute`). Each child domain must be aggregated independently in separate CTEs and joined via `CROSS JOIN` (for single-row KPIs) or `FULL/LEFT JOIN` on a shared dimension key.
- **Source Location:** `payments.txt §2 (G3)`
- **Status:** Documented & Enforced (Verified L3)
- **Mathematical Impact:**
  - Joining 2 refunds with 2 dispute records produces a Cartesian product of 4 rows.
- **Worked Numerical Example:**
  - Merchant M1: 2 refunds totaling AED 300; 2 disputes totaling AED 500.
  - *Direct Cartesian Join:* `SUM(refund_amount) = AED 600`, `SUM(dispute_amount) = AED 1,000` (Doubled).
  - *Correct Disjoint CTEs:*
    ```sql
    WITH ref_agg AS (
        SELECT merchant_id, SUM(refund_amount) AS total_refunds
        FROM refund GROUP BY merchant_id
    ),
    disp_agg AS (
        SELECT merchant_id, SUM(dispute_amount) AS total_disputes
        FROM dispute GROUP BY merchant_id
    )
    SELECT 
        m.merchant_id,
        COALESCE(r.total_refunds, 0) AS total_refunds,
        COALESCE(d.total_disputes, 0) AS total_disputes
    FROM merchant m
    LEFT JOIN ref_agg r ON m.merchant_id = r.merchant_id
    LEFT JOIN disp_agg d ON m.merchant_id = d.merchant_id;
    ```

### RULE-010: Multi-Currency Isolation (No Cross-Currency Summation)
- **Domain Area:** Multi-Currency Financial Governance
- **Statement:** The payments data model contains no foreign exchange (FX) conversion table. Transactions occur across multiple currencies (`AED`, `ZAR`, `EGP`, `JOD`, `USD`). System queries must **never** execute `SUM(amount)` without grouping by `currency`.
- **Source Location:** `payments.txt §1`
- **Status:** Documented & Enforced (Verified L3)
- **Constraint Formula:**
  ```text
  Valid Query: SELECT currency, SUM(amount) FROM financial_transaction GROUP BY currency
  Invalid Query: SELECT SUM(amount) FROM financial_transaction
  ```
- **Worked Example:**
  - Transactions: 10,000 JOD, 50,000 AED, 2,000 USD.
  - Cross-summing produces `62,000` (meaningless, economically invalid number).
  - Grouping preserves correct monetary values by currency bucket.

---

### RULE-011: Interchange, MDR & Scheme Fee Net Settlement Calculation
- **Domain Area:** Payments Revenue & Settlement
- **Statement:** Merchant Net Settlement is computed as Gross Captured Amount minus Merchant Discount Rate (MDR). Acquirer Net Margin is computed as MDR minus Interchange Fee minus Scheme Fee.
- **Source Location:** `payments.txt §4`
- **Status:** Documented & Implemented (Verified L3)
- **Formulas:**
  ```text
  Merchant Net Settlement = Gross Transaction Amount - Total MDR Fee
  Acquirer Net Margin = Total MDR Fee - Interchange Fee - Scheme Fee
  Effective MDR Rate (%) = (Total MDR Fee / Gross Transaction Amount) * 100
  ```
- **Worked Numerical Example:**
  - *Inputs:*
    - Gross Transaction Amount = AED 10,000.00
    - Interchange Fee Rate = 1.20% = AED 120.00
    - Scheme Assessment Fee = 0.15% = AED 15.00
    - Contracted MDR = 1.85% = AED 185.00
  - *Calculations:*
    - Merchant Net Settlement = AED 10,000.00 - AED 185.00 = **AED 9,815.00**
    - Acquirer Net Margin = AED 185.00 - AED 120.00 - AED 15.00 = **AED 50.00** (0.50% Net Spread)
    - Effective MDR Rate = (185.00 / 10,000.00) * 100 = **1.85%**

### RULE-012: Dispute & Chargeback Ratio Calculation
- **Domain Area:** Card Scheme Compliance (Visa/Mastercard)
- **Statement:** Card scheme chargeback ratios are calculated as the count of disputes filed in a calendar month divided by the count of successfully captured transactions in the *same* calendar month, expressed as a percentage or in basis points (bps).
- **Source Location:** `payments.txt §5`
- **Status:** Documented & Implemented (Verified L3)
- **Formula:**
  ```text
  Chargeback Ratio (%) = (Count of Disputes in Month M / Count of Captured Transactions in Month M) * 100
  Chargeback Ratio (bps) = Chargeback Ratio (%) * 100
  ```
- **Thresholds:**
  - Standard Monitoring: > 0.65% (65 bps)
  - Excessive / Fine Threshold: > 0.90% (90 bps)
- **Worked Numerical Example:**
  - *Inputs:* Month = September 2026.
    - Captured Transactions = 50,000
    - Disputes Filed = 42
  - *Calculation:*
    - Chargeback Ratio = (42 / 50,000) * 100 = **0.084%** (8.4 bps)
  - *Compliance Status:* Clean (Well below 65 bps monitoring threshold).

## 4. Supply Chain Finance (FlexCap) Business Rules

### RULE-013: Invoice vs Creation Date Disambiguation
- **Domain Area:** Invoice Discounting & Factoring
- **Statement:** The system must strictly distinguish between the business event date (`invoice_raised_date` / `due_date`) and the system audit record timestamp (`created_date_time`). Business queries asking for monthly or quarterly volume must filter by `invoice_raised_date`.
- **Source Location:** `docs/FlexCap_ToDo.xlsx:Sheet1 (Issue #3)`
- **Status:** Documented (Confirmed Defect in older test runs, addressed in semantic notes)
- **Worked Example:**
  - Invoice #INV-1001 raised by vendor on `2026-05-15`.
  - Batch data migration loaded into the database on `2026-06-02`.
  - User Question: "Show invoices raised in May 2026."
  - *Correct Filter:* `WHERE invoice_raised_date >= '2026-05-01' AND invoice_raised_date < '2026-06-01'`
  - *Incorrect Filter:* `WHERE created_date_time >= '2026-05-01' AND created_date_time < '2026-06-01'` (Silently misses the invoice).

### RULE-014: Supply Chain Finance Early Payment Discounting & Margin
- **Domain Area:** Working Capital Finance
- **Statement:** When an invoice is discounted before maturity, the financier disburses the invoice amount minus the financing discount fee. The discount fee is calculated based on annual interest rate, days to maturity, and invoice principal.
- **Source Location:** `docs/FlexCap_ToDo.xlsx:Sheet1 (Issue #1, #7)`
- **Status:** Documented & Implemented (Verified L3)
- **Formula:**
  ```text
  Financing Tenor (Days) = invoice_due_date - disbursement_date
  Discount Fee = invoice_amount * (annual_discount_rate / 365) * Financing Tenor
  Disbursed Amount = invoice_amount * advance_rate - Discount Fee
  Financier Margin = Discount Fee - Cost of Funds
  ```
- **Worked Numerical Example:**
  - *Inputs:*
    - Invoice Principal = INR 1,000,000.00
    - Advance Rate = 90% (INR 900,000.00)
    - Invoice Raised = 2026-07-01; Due Date = 2026-09-29 (90 days)
    - Disbursement Date = 2026-07-01
    - Annual Discount Rate = 12.00%
    - Cost of Funds = 8.00%
  - *Calculations:*
    - Discount Fee = 1,000,000 * (0.12 / 365) * 90 = **INR 29,589.04**
    - Net Disbursed = (1,000,000 * 0.90) - 29,589.04 = **INR 870,410.96**
    - Cost of Funds = 1,000,000 * (0.08 / 365) * 90 = INR 19,726.03
    - Net Financier Spread/Margin = 29,589.04 - 19,726.03 = **INR 9,863.01**

### RULE-015: Value Grounding & Enum Anti-Fabrication Check
- **Domain Area:** Natural Language Grounding
- **Statement:** Generated SQL literals must be verified against actual distinct column values in the schema or semantic layer. The model must not invent status literals (e.g. fabricating 'Success' when the database uses 'SETTLED' or 'COMPLETED').
- **Source Location:** `docs/FlexCap_ToDo.xlsx:Sheet1 (Issue #1)`, `backend/app/filter_options.py`
- **Status:** Implemented via Semantic Layer Glossary & Profile Notes (Verified L3)
- **Allowed Status Sets (Payments / FlexCap):**
  - Transaction Status: `{'AUTHORIZED', 'CAPTURED', 'CLEARED', 'SETTLED', 'FAILED', 'REVERSED'}`
  - Payout Status: `{'PROCESSING', 'SETTLED', 'FAILED'}`
  - Invoice Status: `{'DRAFT', 'SUBMITTED', 'APPROVED', 'DISCOUNTED', 'PAID', 'OVERDUE'}`
- **Worked Example:**
  - *User Question:* "Show all successful transactions."
  - *Model Action:* Semantic layer mapping instructs: `"successful" translates to ft.status IN ('CAPTURED', 'SETTLED')`.
  - *Grounding Check:* Verifies `CAPTURED` and `SETTLED` exist in distinct value profiles; rejects queries attempting `status = 'Success'`.
